# История проверок фида и сверка с предыдущей версией — дизайн

Дата: 2026-07-23

## 1. Что автоматизируем

Сейчас «Анализатор фида» — разовый инструмент: загрузил файл, посмотрел метрики, закрыл вкладку — результат исчез. Партнёр (карточка в канбане «Партнёры в работе») никак не связан с тем, что происходило при проверке его фида, и повторные проверки не с чем сравнить.

Задача: при каждой загрузке фида спрашивать, для какого партнёра эта проверка — новый или уже проверявшийся ранее — сохранять результат на бэкенде, и для повторных партнёров сразу показывать сравнение с их последней сохранённой проверкой.

**Не входит в объём этого этапа:**
- Потоварный (SKU-level) diff — сравниваем только агрегированные метрики, которые уже считает `renderAnalytics()`. Полное сравнение по товарам — возможное развитие позже, схема к этому готова (можно добавить колонку с сырыми товарами без слома текущей).
- Выбор конкретной исторической версии для сравнения — сравнение всегда идёт с самой свежей предыдущей проверкой этого партнёра. Полная история при этом всё равно сохраняется в БД на будущее, просто в API/UI сейчас не выбирается.
- Права доступа к истории — общая для всей команды, как и весь остальной проект (без ролей).

## 2. Данные

Новая таблица `feed_analyses`, партнёр — та же сущность, что в канбане «Партнёры в работе» (`partners.id`), без отдельной параллельной сущности.

```sql
CREATE TABLE feed_analyses (
  id          SERIAL PRIMARY KEY,
  partner_id  INTEGER NOT NULL REFERENCES partners(id) ON DELETE CASCADE,
  format      TEXT NOT NULL CHECK (format IN ('xml', 'xlsx')),
  metrics     JSONB NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_feed_analyses_partner_created ON feed_analyses (partner_id, created_at DESC);
```

`metrics` — плоский объект агрегатов, которые анализатор уже считает на клиенте в `renderAnalytics()` (`total`, `inStock`/`outStock`, `titleFilled`, `titlesWithSize`, `withMain`, `with2plus`, `noExtra`, `brandFilled`, `noBrand`, `colorFilled`, `colorInvalid`, `sizeFilled`, `sizeIssues`, `descFilled`, `descOk`, `descShort`, `catFilled`, `catShallow`, `noCat`, `groupFilled`, `noGroup`, плюс аналогичные по gender/age_group). Никакой новой логики подсчёта не вводится — просто сериализуется то, что уже вычислено.

`ON DELETE CASCADE` — если партнёра удаляют из канбана, история его проверок фида удаляется вместе с ним (не остаётся сиротских записей).

Индекс по `(partner_id, created_at DESC)` — под ровно два запроса, которые нужны API: «есть ли у партнёра хоть одна проверка» и «последняя проверка партнёра».

## 3. API

Тот же паттерн авторизации, что у `/api/partners` и `/api/integration`: `requireAuth` + `verifyCsrf` на мутирующих запросах.

| Метод | Путь | Тело | Описание |
|---|---|---|---|
| GET | `/api/partners/with-analyses` | — | Партнёры, у которых есть ≥1 сохранённая проверка, с датой последней (для экрана «Повторный»). |
| GET | `/api/feed-analyses/latest?partner_id=X` | — | Последняя сохранённая проверка партнёра (метрики + дата) или `null`, если проверок ещё не было. |
| POST | `/api/feed-analyses` | `{partner_id, format, metrics}` | Сохранить новый снимок после того как клиент посчитал анализ. |

`GET /api/partners/with-analyses` реализуется через `SELECT DISTINCT ON (partner_id) ...` или `JOIN` с группировкой — возвращает список `{id, name, type, last_checked_at}`, отсортированный по `last_checked_at DESC` (последние проверенные — сверху, естественный порядок для поиска «кого недавно проверяли»).

## 4. Фронтенд

**Шаг 1 — при выборе файла (до парсинга)** показываем модалку с тремя вариантами:
- **Новый партнёр** — форма имя + тип (api/mall), как в модалке «Добавить партнёра» канбана. Перед отправкой сверяем имя (без учёта регистра) со списком уже существующих партнёров (тем же, что использует канбан, `GET /api/partners`) — если совпадение есть, показываем предупреждение «Партнёр с таким именем уже есть в канбане — точно новый?» с возможностью подтвердить (создать всё равно, вдруг тёзка) или отменить. Без совпадения — `POST /api/partners` сразу (создаёт карточку в канбане со стадией `s0`, как обычное добавление) → переходим к шагу 2. Это защита от случайного дубля для партнёра, который уже в канбане, но ещё ни разу не проверялся (и поэтому не появится в списке «Повторный», где показаны только партнёры с историей).
- **Повторный** — список из `GET /api/partners/with-analyses` с поиском по имени → выбор партнёра → сразу к шагу 2, без дополнительного выбора версии.
- **Пропустить** — анализ без привязки к партнёру и без сохранения (текущее поведение как есть — для разовых проверок «на посмотреть»).

**Шаг 2 — парсинг и рендер** — существующая логика (`renderAnalytics`, `renderFields`, `renderItems`) не меняется.

**Шаг 3 — после успешного рендера:**
- Отправляем `POST /api/feed-analyses` с посчитанными метриками (фоново, не блокирует уже показанные результаты; при неудаче — `logErr`, без вмешательства в UI).
- Если был выбран «Повторный»: запрашиваем `GET /api/feed-analyses/latest?partner_id=X` **до** сохранения нового снимка (иначе только что сохранённая проверка станет «последней» сама для себя) и рендерим блок **«Сравнение с последней проверкой»** над обычной аналитикой — те же метрики, что в карточках анализатора, было→стало, стрелка и цвет (зелёный — улучшилось, красный — ухудшилось, серый — без изменений).

Порядок операций на шаге 3 важен: сначала GET latest (старый снимок), потом POST нового — иначе сравнивать не с чем.

## 5. Обработка ошибок

- Не удалось создать нового партнёра (сеть/валидация) — ошибка показывается в модалке, к анализу не переходим.
- `GET /api/partners/with-analyses` вернул пустой список — сообщение «пока нет проверенных партнёров» вместо пустого списка.
- `POST /api/feed-analyses` после анализа не удался — результаты анализа уже показаны, не откатываются; только `logErr`.
- `GET /api/feed-analyses/latest` вернул `null` (у выбранного партнёра на самом деле нет сохранённых проверок — гонка, например кто-то параллельно удалил партнёра) — блок сравнения просто не показывается, без ошибки на экране.

## 6. Тестирование

- **Бэкенд** (jest + supertest + pg-mem, тот же паттерн, что у partners/integration API): создание анализа с валидными/невалидными данными, список `with-analyses` пустой/непустой, `latest` для партнёра без истории возвращает `null`, требование сессии и CSRF на `POST`.
- **Фронтенд** — автотестов нет (нет браузера в этом окружении для проверки drag/drop-подобного взаимодействия с модалками), верификация — код-ревью новых обработчиков + ручной смоук-тест на живом деплое после выкладки.
