# Категорийная приоритезация полей фида — дизайн

Дата: 2026-09-10

## 1. Что автоматизируем

Сейчас «Анализатор фида» проверяет условные поля одним и тем же способом для всех товаров — поле либо `req:true` (всегда обязательно), либо `req:false` (необязательно, все условные поля сейчас в этой корзине). Реальная значимость поля зависит от категории товара: `brand` критичен почти везде, но необязателен для Товаров для дома; `color` критичен для Электроники и Аксессуаров, но лишь средней важности для Одежды.

**Согласованный со мной список полей и базовая обязательность** (правки в интерактивной таблице `ratings/matrix`, зафиксировано 2026-09-08):
- **Всегда обязательно, не зависит от категории** (8 полей): `id`, `title`, `description`, `image_link`, `availability`, `price`, `additional_image_link` (минимум 3 изображения), `product_type` (передаётся полное дерево категорий).
- **Не обязателен**: `link` — раньше входил в базовые, по факту в реальном фиде BCC Mall не обязателен.
- **Условные, приоритет зависит от категории** (8 полей): `brand`, `color`, `size`, `size_system`, `gender`, `age_group`, `item_group_id`, `sale_price`.
- **Убраны из проверки совсем**: `material`, `pattern`, `condition`, `product_highlight`, `energy_efficiency_class` — таких тегов в реальном фиде BCC Mall нет (проверено по выгрузке `Лист Microsoft Excel (2).xlsx`).

Задача: определять категорию **каждого товара** внутри фида автоматически, применять к нему приоритеты этой категории (критично/средне/необязательно вместо плоского req:true/false) для 8 условных полей, и показывать результаты проверки с учётом этого — разбивку по категориям и пересчитанные по тиру рекомендации.

**Не входит в объём:**
- Изменения бэкенда — вся логика клиентская, «Анализатор фида» как был вне периметра бэкенда (спека 2026-07-21, раздел 1), так и остаётся.
- Вкладка «Заполненность полей» (общий % по каждому полю на весь фид) — остаётся как есть, без разбивки по категориям; новая панель категорий полностью закрывает этот разрез отдельно.
- Ручной выбор категории оператором — детекция полностью автоматическая (см. раздел 3), это решение принято явно: категория определяется на уровне каждого товара, вручную протегать тысячи позиций нереально.

## 2. Матрица приоритетов (данные)

12 категорий × 8 условных полей, тир — `critical` / `medium` / `optional`. Источник — интерактивная таблица правок (`ratings/matrix`, зафиксировано 2026-09-08, версия 104), не черновик из раздела 1 прежней версии этой спеки. Хранится как JS-объект `CATEGORY_FIELD_TIERS` рядом с существующими `FIELDS`/`CHECKLISTS` в `public/index.html`.

Категории «Обувь» и «Одежда» разделены (раньше была одна «Одежда и обувь») — сейчас у них одинаковая матрица (Обувь заполнена как копия Одежды по моей просьбе), но детекция и панель разбивки должны считать их раздельно. Категории «Книги, музыка и фильмы», «Подарки и сувениры», «Школа и творчество» — новые, их тиры предложены по общей логике фида, а не моей собственной оценкой, и помечены отдельно.

## 3. Детекция категории товара

Каждый товар проверяется независимо (см. раздел «Открытые вопросы» дизайна от 2026-07-23: категория — атрибут товара, не всего фида, решение подтверждено в этой сессии).

**Сигнал:** `product_type` (уже парсится, путь вида «Одежда > Мужская > Футболки»), при отсутствии совпадения — `title`. `google_product_category` не читается анализатором и не добавляется в объём этой задачи — сигнала `product_type`+`title` достаточно для MVP.

**Механизм:** словарь `CATEGORY_KEYWORDS` — на каждую категорию список ключевых слов/подстрок (регистронезависимо). Проверка идёт по фиксированному порядку категорий (сначала более узкие по словарю, чтобы не терять специфичные термины на общих словах), первое совпадение побеждает:

1. **Детские товары** — детск, для детей, малыш, младенец, новорожденн, подгузник, коляск, автокресл, погремушк, пелёнк
2. **Электроника** — смартфон, телефон, ноутбук, компьютер, планшет, наушник, умные час, смарт-час, фитнес-браслет, умная колонк, телевизор, пылесос, фен, блендер, кабель, зарядн, powerbank, повербанк, фотоаппарат, увлажнитель воздух, очиститель воздух
3. **Ювелирные изделия** — кольцо, кольца, серьг, цепочк, кулон, подвеск, ювелир, брошь, запонк, ожерель, браслет
4. **Спортивные товары** — тренажёр, гантел, штанг, гиря, велосипед, самокат, ролики, коврик для йоги, скакалк, эспандер, беговая дорожк, наколенник, налокотник
5. **Аксессуары** — сумк, рюкзак, чехол, ремень, кошелёк, портмоне, шарф, перчатк, шапк, очки солнцезащитн, зонт
6. **Обувь** — обувь, кроссовк, ботинк, туфли, сапог, сандал
7. **Одежда** — одежд, футболк, рубашк, брюки, джинс, платье, юбк, куртк, пальто, свитер, толстовк, шорты, костюм, бельё
8. **Красота и здоровье** — крем, сыворотк, шампунь, парфюм, дух, туалетная вода, тушь, помад, тональн, витамин, БАД, космети, уход за кож, уход за волос
9. **Товары для дома** — мебель, посуд, кастрюл, сковород, постельн, полотенц, штор, светильник, лампа, ковёр, декор для дома, кухонн утвар

Порядок в основном узкое-перед-широким (детские товары, ювелирка, спорт, аксессуары, обувь — раньше широких одежды/красоты/дома), с одним явным исключением: Электроника стоит на 2-м месте, раньше Ювелирки, хотя её словарь не «широкий» — это разрешает конфликт «браслет» (голое слово — ювелирное изделие) против «фитнес-браслет»/«смарт-браслет» (Электроника). При простом посимвольном substring-поиске (без учёта границ слов) «фитнес-браслет» содержит «браслет» как подстроку, поэтому если бы Ювелирка проверялась первой, она бы перехватывала и фитнес-браслеты тоже. Электроника со своими составными фразами обязана проверяться раньше Ювелирки с её голым «браслет» — иначе конфликт не решается, а инвертируется. (Обнаружено и исправлено на этапе ревью реализации: изначальная версия этого раздела утверждала обратный порядок — ошибка, которая не проявлялась, пока в словарь Ювелирки не добавили само слово «браслет».) Обувь вынесена перед Одеждой отдельным пунктом, потому что раньше это был один список «Одежда и обувь» — теперь это две категории с одинаковой матрицей приоритетов (раздел 2), но их всё равно нужно различать для панели разбивки в разделе 4. Список не претендует на полноту с первого раза — это эвристика, расширяемая по мере находок на реальных фидах.

**Открыто — нет словаря:** для «Книги, музыка и фильмы», «Подарки и сувениры», «Школа и творчество» (новые категории из раздела 2, тиры для которых ещё не мои, а предложенные) ключевые слова ещё не согласованы. До того, как они появятся, детекция для них не сработает — товары этих категорий будут уходить в «Категория не определена» ниже. Нужно отдельно согласовать словари для этих трёх, прежде чем реализовывать раздел 3 целиком.

**Не найдено совпадение ни по `product_type`, ни по `title`:** товар помечается `category: null`, попадает в бакет «Категория не определена» — не пропускается молча, не участвует в тирированных рекомендациях (только в общих базовых проверках 8 обязательных полей), и отдельно показывается оператору для ручной доразметки.

## 4. Разбивка по категориям (новая панель)

Новая функция `detectCategory(item)` возвращает ключ категории (`odezhda`/`dom`/.../`juvelirka`) или `null`. При рендере результатов товары группируются по результату детекции.

Новая панель **«Разбивка по категориям»**, в начале результатов, перед существующими карточками (Товары, Названия, Фото и т.д. — те остаются без изменений, общими на весь фид). На каждую обнаруженную категорию:
- количество товаров;
- процент заполненности **только критичных для этой категории** полей (не общий % по всем 8 условным полям — конкретно те, что в `CATEGORY_FIELD_TIERS[категория]` помечены `critical`).

Отдельная строка — «Категория не определена: N товаров», с возможностью посмотреть список этих товаров (аналогично существующим detail-таблицам в `renderAnalytics`).

## 5. Пересчёт рекомендаций

Текущая логика (клиентская, в `renderAnalytics`): одна рекомендация на поле на весь фид с фиксированной серьёзностью (`err`/`warn`/`info`), например «Заполните бренд — не заполнен у N товаров».

Новая логика — для каждого условного поля товары, у которых оно не заполнено, разбиваются по тиру их категории:
- **critical** → рекомендация уровня `err`, охватывает только те товары, где поле критично для их категории;
- **medium** → рекомендация уровня `warn`, для товаров, где поле среднее;
- **optional** → в рекомендации не попадает вообще.

Товары с неопределённой категорией (`category: null`) в тирированные рекомендации по условным полям не попадают (нет данных, чтобы определить тир) — только в свою собственную строку «Категория не определена» из раздела 4.

Базовые 8 полей (id/title/description/image_link/availability/price/additional_image_link/product_type) — рекомендации по ним не меняются, остаются как сейчас, вне зависимости от категории. `link` в рекомендации не попадает вовсе — он необязателен.

## 6. Тестирование

Вся логика клиентская — автотестов в этом окружении нет (браузера нет), как и во всех предыдущих фронтенд-задачах этого проекта. Верификация: код-ревью на соответствие матрице и словарю из разделов 2–3, ручной смоук-тест с реальным фидом (в идеале — тем же Xiaomi-примером с bccmall.kz, где уже видели смешение смартфонов/ТВ/носимых/техники) после деплоя.
