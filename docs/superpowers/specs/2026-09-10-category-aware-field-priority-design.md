# Категорийная приоритезация полей фида — дизайн

Дата: 2026-09-10

## 1. Что автоматизируем

Сейчас «Анализатор фида» проверяет 15 условных полей (`brand`, `color`, `size`, `gender`, `age_group`, `condition`, `sale_price`, `product_type`, `material`, `pattern`, `additional_image_link`, `item_group_id`, `product_highlight`, `energy_efficiency_class`, `size_system`) одним и тем же способом для всех товаров — поле либо `req:true` (всегда обязательно, 6 базовых полей: title/description/link/image_link/availability/price), либо `req:false` (необязательно, все 15 условных полей сейчас в эту корзину). Реальная значимость поля зависит от категории товара: `brand` критичен для Электроники и Аксессуаров, но необязателен для Товаров для дома; `energy_efficiency_class` критичен только для Электроники и бессмыслен для остальных 7 категорий.

Задача: определять категорию **каждого товара** внутри фида автоматически, применять к нему приоритеты этой категории (критично/средне/необязательно вместо плоского req:true/false), и показывать результаты проверки с учётом этого — разбивку по категориям и пересчитанные по тиру рекомендации.

**Не входит в объём:**
- Изменения бэкенда — вся логика клиентская, «Анализатор фида» как был вне периметра бэкенда (спека 2026-07-21, раздел 1), так и остаётся.
- Вкладка «Заполненность полей» (общий % по каждому полю на весь фид) — остаётся как есть, без разбивки по категориям; новая панель категорий полностью закрывает этот разрез отдельно.
- Ручной выбор категории оператором — детекция полностью автоматическая (см. раздел 3), это решение принято явно: категория определяется на уровне каждого товара, вручную протегать тысячи позиций нереально.

## 3. Детекция категории товара

Каждый товар проверяется независимо (см. раздел «Открытые вопросы» дизайна от 2026-07-23: категория — атрибут товара, не всего фида, решение подтверждено в этой сессии).

**Сигнал:** `product_type` (уже парсится, путь вида «Одежда > Мужская > Футболки»), при отсутствии совпадения — `title`. `google_product_category` не читается анализатором и не добавляется в объём этой задачи — сигнала `product_type`+`title` достаточно для MVP.

**Механизм:** словарь `CATEGORY_KEYWORDS` — на каждую категорию список ключевых слов/подстрок (регистронезависимо). Проверка идёт по фиксированному порядку категорий (сначала более узкие по словарю, чтобы не терять специфичные термины на общих словах), первое совпадение побеждает:

1. **Детские товары** — детск, для детей, малыш, младенец, новорожденн, подгузник, коляск, автокресл, погремушк, пелёнк
2. **Ювелирные изделия** — кольцо, кольца, серьг, цепочк, кулон, подвеск, ювелир, брошь, запонк, ожерель
3. **Спортивные товары** — тренажёр, гантел, штанг, гиря, велосипед, самокат, ролики, коврик для йоги, скакалк, эспандер, беговая дорожк, наколенник, налокотник
4. **Аксессуары** — сумк, рюкзак, чехол, ремень, кошелёк, портмоне, шарф, перчатк, шапк, очки солнцезащитн, зонт
5. **Электроника** — смартфон, телефон, ноутбук, компьютер, планшет, наушник, умные час, смарт-час, фитнес-браслет, умная колонк, телевизор, пылесос, фен, блендер, кабель, зарядн, powerbank, повербанк, фотоаппарат, увлажнитель воздух, очиститель воздух
6. **Одежда и обувь** — одежд, футболк, рубашк, брюки, джинс, платье, юбк, куртк, пальто, свитер, толстовк, шорты, костюм, обувь, кроссовк, ботинк, туфли, сапог, сандал, бельё
7. **Красота и здоровье** — крем, сыворотк, шампунь, парфюм, дух, туалетная вода, тушь, помад, тональн, витамин, БАД, космети, уход за кож, уход за волос
8. **Товары для дома** — мебель, посуд, кастрюл, сковород, постельн, полотенц, штор, светильник, лампа, ковёр, декор для дома, кухонн утвар

Порядок явно осознанный: узкоспециализированная лексика (детские товары, ювелирка, спорт, аксессуары) проверяется раньше широких категорий (одежда, красота, дом), чтобы специфичные термины не терялись на пересечениях (пример конфликта: «браслет» — ювелирное изделие или фитнес-браслет из Электроники; решается тем, что словарь Электроники использует составные фразы «фитнес-браслет»/«смарт-браслет», а не голое слово «браслет», и проверяется после ювелирки). Список не претендует на полноту с первого раза — это эвристика, расширяемая по мере находок на реальных фидах.

**Не найдено совпадение ни по `product_type`, ни по `title`:** товар помечается `category: null`, попадает в бакет «Категория не определена» — не пропускается молча, не участвует в тирированных рекомендациях (только в общих базовых проверках 6 обязательных полей), и отдельно показывается оператору для ручной доразметки.

## 4. Разбивка по категориям (новая панель)

Новая функция `detectCategory(item)` возвращает ключ категории (`odezhda`/`dom`/.../`juvelirka`) или `null`. При рендере результатов товары группируются по результату детекции.

Новая панель **«Разбивка по категориям»**, в начале результатов, перед существующими карточками (Товары, Названия, Фото и т.д. — те остаются без изменений, общими на весь фид). На каждую обнаруженную категорию:
- количество товаров;
- процент заполненности **только критичных для этой категории** полей (не общий % по всем 15 полям — конкретно те, что в `CATEGORY_FIELD_TIERS[категория]` помечены `critical`).

Отдельная строка — «Категория не определена: N товаров», с возможностью посмотреть список этих товаров (аналогично существующим detail-таблицам в `renderAnalytics`).

## 5. Пересчёт рекомендаций

Текущая логика (клиентская, в `renderAnalytics`): одна рекомендация на поле на весь фид с фиксированной серьёзностью (`err`/`warn`/`info`), например «Заполните бренд — не заполнен у N товаров».

Новая логика — для каждого условного поля товары, у которых оно не заполнено, разбиваются по тиру их категории:
- **critical** → рекомендация уровня `err`, охватывает только те товары, где поле критично для их категории;
- **medium** → рекомендация уровня `warn`, для товаров, где поле среднее;
- **optional** → в рекомендации не попадает вообще.

Товары с неопределённой категорией (`category: null`) в тирированные рекомендации по условным полям не попадают (нет данных, чтобы определить тир) — только в свою собственную строку «Категория не определена» из раздела 4.

Базовые 6 полей (title/description/link/image_link/availability/price) — рекомендации по ним не меняются, остаются как сейчас, вне зависимости от категории.

## 6. Тестирование

Вся логика клиентская — автотестов в этом окружении нет (браузера нет), как и во всех предыдущих фронтенд-задачах этого проекта. Верификация: код-ревью на соответствие матрице и словарю из разделов 2–3, ручной смоук-тест с реальным фидом (в идеале — тем же Xiaomi-примером с bccmall.kz, где уже видели смешение смартфонов/ТВ/носимых/техники) после деплоя.
