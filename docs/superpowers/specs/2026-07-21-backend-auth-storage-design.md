# Merchant Tools: бэкенд, хранение в БД и авторизация — дизайн

Дата: 2026-07-21

## 1. Что автоматизируем / зачем

Сейчас Merchant Tools — статический `index.html` без бэкенда, все данные (канбан «Партнёры в работе», чек-лист «Интеграция») либо живут в `localStorage` одного браузера, либо (чек-лист «Интеграция») вообще не сохраняются и сбрасываются при перезагрузке страницы. Команда небольшая (до ~20 человек), нужен общий бэкенд с БД, чтобы:

- данные канбана и чек-листов были общими для всей команды, а не заперты в браузере одного человека;
- доступ к приложению был закрыт логином.

**Вне объёма этого этапа:** «Анализатор фида» и «Создание логотипа» — остаются как есть, чисто клиентские инструменты без собственных данных на бэкенде (они не хранят ничего, кроме результата разовой обработки загруженного файла в рамках текущей сессии браузера). Изменение для них — только то, что вся страница целиком теперь требует авторизации.

## 2. Пользователи и доступ

- Небольшая команда (примерно до ~20 человек), доступ выдаётся вручную — самостоятельной регистрации нет.
- Роли не нужны: у всех авторизованных пользователей одинаковые права (создание/редактирование/удаление партнёров, редактирование чек-листов).
- Пользователей заводит администратор через CLI-скрипт (`server/scripts/create-user.js`), задавая логин и пароль напрямую в БД (хеш bcrypt) — без веб-формы регистрации.

## 3. Архитектура и стек

- **Бэкенд:** Node.js + Express.
- **БД:** managed Postgres у того же провайдера, что и хостинг.
- **Хостинг:** Railway или Render (выбор конкретного провайдера — на этапе имплементации, в дизайне не фиксируется).
- **Фронтенд:** текущий `index.html` переезжает из корня репозитория в `public/index.html` и отдаётся тем же Express-сервером статически. Один процесс, один деплой — без отдельного фронтенд-хостинга.

Структура репозитория:

```
merchant-tools/
  server/
    index.js
    db/schema.sql
    routes/
      auth.js
      partners.js
      integration.js
    middleware/
      auth.js        (проверка сессии)
      csrf.js
      rateLimit.js
    scripts/
      create-user.js
  public/
    index.html
  package.json
  .env.example
  docs/superpowers/specs/  (этот файл)
```

## 4. Модель данных (Postgres)

```sql
CREATE TABLE users (
  id            SERIAL PRIMARY KEY,
  username      TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- таблица session создаётся автоматически connect-pg-simple (sid, sess jsonb, expire)

CREATE TABLE partners (
  id         SERIAL PRIMARY KEY,
  name       TEXT NOT NULL,
  type       TEXT NOT NULL CHECK (type IN ('api', 'mall')),
  stage      TEXT NOT NULL DEFAULT 's0',
  checks     JSONB NOT NULL DEFAULT '{}',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE integration_checklist (
  type       TEXT PRIMARY KEY CHECK (type IN ('api', 'mall')),
  checks     JSONB NOT NULL DEFAULT '{}',
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Пояснения:

- `partners.checks` — персональный чек-лист каждой карточки канбана, как сейчас в модели карточки (`{id, name, type, stage, checks}`), просто переезжает из `localStorage` в БД без изменения формата.
- `integration_checklist` — состояние вкладки «Интеграция», **общее на всю команду**, по одной строке на трек (`api`/`mall`). Не привязано к конкретному партнёру и остаётся раздельной сущностью от `partners.checks` (по явному решению — не объединять эти два места).
- `stage` хранится как текст с проверкой по значениям текущего справочника стадий (`s0`…`s8`, `s6b`) — без отдельной таблицы-справочника, т.к. список стадий фиксирован в коде фронтенда и не редактируется пользователем.

## 5. Авторизация и безопасность

**Механизм:** серверные сессии, не JWT.

- Cookie сессии: `httpOnly`, `secure`, `sameSite=lax`.
- Хранилище сессий — та же Postgres-БД через `connect-pg-simple` (не in-memory).
- Session ID ротируется при успешном логине (защита от session fixation).
- Таймаут сессии: 8 часов бездействия — после этого требуется повторный вход. (Значение по умолчанию для MVP, можно поменять на этапе имплементации без изменения архитектуры.)

**Пароли:** bcrypt, cost factor 12. Пароли в открытом виде нигде не логируются и не хранятся.

**Защита от типовых атак:**

| Угроза | Мера |
|---|---|
| CSRF | Токен на все мутирующие запросы (double-submit cookie), т.к. auth на cookie |
| Брутфорс логина | `express-rate-limit`: максимум 5 попыток / 15 минут с одного IP на `/api/login` |
| Заголовки безопасности | `helmet`: CSP, HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy |
| SQL-инъекции | Только параметризованные запросы через `pg`, никакой конкатенации строк в SQL |
| Некорректный/вредоносный ввод | Валидация каждого эндпоинта схемами `zod` — типы, длины строк, допустимые enum-значения (`type`, `stage`), отклонение неизвестных полей |
| Перехват трафика | HTTPS принудительно (TLS терминируется хостинг-провайдером) |
| Избыточные права БД | Приложение подключается под отдельным непривилегированным пользователем Postgres, не суперюзером |
| Утечка секретов | `DATABASE_URL`, `SESSION_SECRET` — только через переменные окружения хостинга; `.env` в `.gitignore`; в репозитории только `.env.example` |
| Утечка внутренних деталей при ошибках | Клиенту — только безопасные сообщения (401/400 с понятным текстом); полный стектрейс — только в серверный лог, никогда в ответ API |

**Периметр логина:** всё приложение целиком закрыто авторизацией, включая «Анализатор фида» и «Создание логотипа» — при отсутствии валидной сессии фронтенд показывает экран входа вместо любой страницы приложения.

## 6. API

Все эндпоинты, кроме `POST /api/login`, требуют валидную сессию (иначе `401`). Все мутирующие запросы (`POST`/`PATCH`/`PUT`/`DELETE`) дополнительно требуют корректный CSRF-токен (иначе `403`).

**Auth**

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/api/login` | `{username, password}` | Ставит cookie сессии; `200` с данными пользователя или `401` при неверных данных |
| POST | `/api/logout` | — | Завершает сессию |
| GET | `/api/me` | — | Текущий пользователь (`200`) или `401`, если сессии нет — фронт использует это для решения, показывать логин или приложение |

**Партнёры**

| Метод | Путь | Тело | Описание |
|---|---|---|---|
| GET | `/api/partners` | — | Список всех партнёров |
| POST | `/api/partners` | `{name, type}` | Создать партнёра (стадия по умолчанию `s0`, `checks: {}`) |
| PATCH | `/api/partners/:id` | `{stage?, checks?, name?, type?}` | Частичное обновление (перетаскивание карточки, правка чек-листа, переименование) |
| DELETE | `/api/partners/:id` | — | Удалить партнёра |

**Интеграция**

| Метод | Путь | Тело | Описание |
|---|---|---|---|
| GET | `/api/integration/:type` | — | `type` = `api` \| `mall`; текущее состояние чек-листа |
| PUT | `/api/integration/:type` | `{checks}` | Полная замена состояния чек-листа для данного трека |

## 7. Изменения во фронтенде (`public/index.html`)

- Новый экран логина, показывается до первого успешного `GET /api/me`; при `401` в любой момент (истекла сессия) — редирект на экран логина.
- `loadPartners()` / `savePartners()` перестают читать/писать `localStorage['merchant_tools_partners']`, становятся асинхронными вызовами к `/api/partners` — создание, перетаскивание карточки, правка чек-листа и удаление сразу уходят на сервер (`POST`/`PATCH`/`DELETE`) без промежуточного слоя в localStorage.
- Вкладка «Интеграция» при открытии тянет состояние через `GET /api/integration/:type`; изменение чекбоксов отправляет `PUT` с небольшим debounce (не на каждый клик отдельным запросом).
- Кнопка «Выйти» в шапке — вызывает `POST /api/logout` и возвращает на экран логина.
- Экспорт/импорт JSON у канбана — остаются как есть, как дополнительное удобство поверх БД, не как основной источник данных.
- «Анализатор фида» и «Создание логотипа» — без изменений в логике, кроме того что доступны только после логина.

## 8. Тестирование

- **Юнит-тесты:** хеширование/проверка пароля (bcrypt), создание и валидация сессии.
- **Интеграционные тесты** (`supertest` поверх Express-приложения и тестовой БД):
  - логин: успех, неверный пароль, срабатывание рейт-лимита после 5 попыток;
  - CRUD партнёров: с валидной сессией — успех; без сессии — `401`;
  - мутирующий запрос без CSRF-токена — `403`;
  - чтение/запись чек-листа интеграции по обоим трекам (`api`, `mall`).

## 9. Деплой

- Railway или Render (конкретный выбор — на этапе имплементации).
- Переменные окружения (`DATABASE_URL`, `SESSION_SECRET`) — через секрет-хранилище провайдера, не в репозитории.
- `server/db/schema.sql` прогоняется один раз при первом деплое для создания таблиц.
- Сразу после первого деплоя — ручной завод первого пользователя через `server/scripts/create-user.js`.
